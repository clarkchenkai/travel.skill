# 数据、隐私与跨国适配

## 1. 三层数据，不维护三套互相矛盾的事实

| 层 | 用途 | 更新方式 |
| --- | --- | --- |
| 原件与工作事实 | 订单、材料、用户确认、冲突与来源 | 原件不改；在现有工作数据中归并 |
| 受众可见快照 | 网页与云端构建可读取的旅行资料 | 按明确公开范围生成，不能靠CSS隐藏 |
| 用户操作状态 | 勾选、新增、删除、当前卡/展开偏好 | 稳定ID关联，不覆盖基础旅行事实 |

travel.md保留当前决定和入口。已有JSON结构就沿用；没有必要不新增第二个真源或自建Ontology。

如果 CI 无权接触私人工作数据，提交已生成、经过审核的公开快照，并让干净构建只读它。主任务修改事实后负责再生成快照；不能让工作树误把旧公开快照当独立真源随意更改。开放模板应使用全新示例数据和干净历史，私有仓库不等于公开网站受保护。

## 2. 可复用的关系模型

下面只是最小示例，不要求迁移现有项目：

~~~json
{
  "trip": {
    "id": "sample-trip",
    "title": "示例旅行 · 2027",
    "startDate": "2027-03-27",
    "endDate": "2027-04-02",
    "locale": "zh-CN",
    "countries": ["FR", "GB"]
  },
  "places": [
    {
      "id": "station-a",
      "name": "车站中文名",
      "localName": "当地站名",
      "timeZone": "Europe/Paris",
      "sourceRefs": ["operator-a"]
    }
  ],
  "days": [
    {
      "id": "day-a",
      "date": "2027-03-27",
      "timeZone": "Europe/Paris",
      "events": [
        {
          "id": "event-a",
          "timeLabel": "抵达后",
          "title": "前往住处",
          "placeIds": ["station-a"],
          "ticketIds": [],
          "sourceRefs": ["operator-a"]
        }
      ]
    }
  ]
}
~~~

日期/时间/ID/币种/国家码使用稳定机器字段，显示文字独立。字母案例、真实站名、票种原名、请求字段不擅自翻译。

状态字段也属于事实：没有订单或用户确认时，用unknown/null/needs-confirmation等明确缺省；**即使只是JSON模板草案，也不能预填confirmed、booked或paid**。用户给出一趟旅行不等于已经订票。

关系核验：所有placeId/ticketId/sourceRef存在；日期完整；事件不重复；票券共享不重复计数；住宿日与转场日一致；私密字段不会通过备注或来源链接再泄漏。

## 3. 全球时间规则

- 航班/固定班次用带偏移的ISO时间，并保留当地 IANA 时区。每个端点分别计算；不要全站只设Asia/Tokyo。
- 时长按UTC绝对时刻之差；显示时刻用端点当地时区。设备所在地不能改变行程事实。
- 跨日期变更线可能“早于出发日期”抵达；不要用自然日顺序误判航班无效。
- 夏令时会产生重复或不存在的钟面时间。遇到只有“01:30”且时区切换不明确，标缺口并查官方/订单，不能静默选一个。
- “第几天”与用户当前计划位置由已选旅行日历规则计算，不代表用户真实定位或真实完成。
- 倒计时过期归零或说明已过；无固定时间的活动不强造倒计时。
- 当天有跨国转场，用事件/端点时区，不能拿当前天的一个时区覆盖全部地点。
- 跨午夜、取还车最晚时刻、登乘截止与酒店入住时段是不同业务含义。

测试至少一条跨区航班、一条午夜边界；涉夏令时/日期线时加对应真实类型的用例。不要只测试日本到中国就宣称全球通过。

## 4. 国家差异按需要核验

| 维度 | 应查什么 | 不应直接复制的案例假设 |
| --- | --- | --- |
| 地图与网络 | 目标用户地区能否访问地图/外链/托管 | Google Maps与pages.dev全球都稳定 |
| 语言 | 中文与当地原名、文字方向、地址格式、字体覆盖 | 所有当地文字都可转成中文 |
| 货币 | ISO币种、小数位、含税/手续费、参考与实付 | 所有¥都是日元，所有价格两位小数 |
| 公共交通 | 预约/检票/上下车/支付、运行日与罢工/停运 | 日本铁路票种、现金习惯可通用 |
| 自驾 | 行驶方向、证件、租赁资格、保障/燃油/异地费 | 看到“国际驾照”就默认合法可租 |
| 徒步与天气 | 季节、日落、步道关闭、补给、撤退线路 | 一张森林图能证明路线安全与难度 |
| 通讯与紧急信息 | 当地服务号码、电话格式、网络准备 | 一个国家号码可用作全球紧急电话 |
| 预订政策 | 时区、截止、退改、人数/年龄限制 | 订单确认即意味着所有关联服务已订 |

这些问题只在与当前旅行有关时处理。查当前官方来源，保存核对日期与原文入口；用户禁止联网时遵守，并把无法核实的时效信息标明。

## 5. 多语言与字体

本地名称用于检索与现场展示；中文用于理解。地名翻译不确定时保留原名，不把两个近似站名合并。

对拉丁扩展、日文、韩文、中文、阿拉伯文或其他文字分别抽样：长名字、换行、输入、复制和地图检索。涉及从右向左书写（RTL）时校验阅读顺序与方向性图标；机场代码/时间等保留可读顺序。不要只看CSS font-family字符串就认为所有字形都已使用目标字体。

## 6. 公开信息边界

先按受众定访问方式：公开、持链接访问但不鉴权、真正受限访问。三者不同。

公开构建通常不应带入：
- 护照/身份证、票号、PNR、订单号、PIN、付款信息、私人联系方式或密钥。
- 原始截图/PDF、内网或含令牌的链接、带敏感信息的文件名。
- 意外藏在备注、HTML注释、JS对象、图片和来源描述中的私人信息。

酒店公开客服电话与私人房东手机不是同一类。真实酒店、具体日期和完整行程本身也可能敏感，按用户的分享范围处理，不能只删字段名就宣称安全。

不要把所有姓名、金额、电话一律当作不可公开字段：匿名显示名、经同意的称呼、预算/票价与商家公开联系电话可按受众授权保留；私人旅客身份、支付凭证和私人联系方式则需单独处理。

检查脚本只能辅助识别结构和明显标记，不能代替自由文本与图片审阅。不要把原始私密数据先提交进Git再指望.gitignore清理历史。


## 7. 只有用户需要时，才增加多人同步

localStorage不能承担多设备共享。用户明确要求同行人共同勾选时，先确定谁可读、谁可写、是否需要账户或受控加入方式，再选择数据服务。最小实现契约：

- 以tripId隔离数据，成员权限由服务端执行，不能只隐藏前端按钮。
- 原始行程与成员操作分离；每条状态用稳定ID，记录修改者、版本或更新时间。
- 明确冲突规则：例如逐事项最后写入，或检测版本冲突后提示；不能让整份清单覆盖别人更新。
- 网络失败显示未同步，重试应幂等，重复提交不生成重复任务。
- 不把可公开读取的链接同时当无边界写入权限；退出/移除成员后应失去写权限。
- 用两份独立登录会话检查：A修改→B看到→B反向修改→A看到；再测未授权写入、离线恢复和跨旅行隔离。
- 没做这些检查只报告本地保存或同步未完成，不能宣称“所有人已同步”。

此分支需要实际后端与访问模型；不为仅需个人路书的项目预建账号、数据库或协作流程。
