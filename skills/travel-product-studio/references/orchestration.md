# 主任务调度与独立工作树（Git worktree）

## 主任务不是转发器

主任务负责：当前决定、共享边界、任务基线、待集成清单、冲突裁决、统一构建、发布与验收。模块任务负责自己的实现和证据。**主任务不得仅收到回执就宣称上线。**

单文件、小改、强耦合改动通常本地做更快。只有独立任务足以覆盖启动、通信、同步和合并成本时才并行。用户明确要左侧可见任务时，创建用户任务；不要把内部子代理冒充侧栏任务。

## 1. 开任务之前

1. 查当前项目、Git 根、工作区改动、远端和实际生产版本。没有 Git 时先确认本次授权是否覆盖建仓；旧“不建仓”与新明确授权冲突时采用新要求。
2. 形成可运行基线。先隔离私人原件、凭证和工作数据，避免初始提交污染整个历史。
3. 只把需要开发和构建的文件纳入版本。构建依赖和公开快照能在干净检出中运行。
4. 明确共享对象的写入人。默认主任务管：数据真源、字体 token、导航/路由、根 HTML、构建白名单、缓存版本和生产发布。
5. 实际查看代码再分工。若全模块挤在 app.js/styles.css，按命名函数/作用域划定范围；合适时拆模块文件，避免整行压缩文件成为长期冲突热点。不为预期冲突而先大重构。

## 2. 推荐的任务边界

| 任务 | 写入范围 | 验收问题 |
| --- | --- | --- |
| 部署 | 构建、托管配置、发布说明 | 指定 main 提交是否真的到同一正式网址 |
| 地图 | 总览、地点目录、地点弹层 | 指向是否正确、网络失败能否退出、是否一击关闭 |
| 日程 | 每日展开、活动、住宿文字、当日图片 | 时间是否可读、完整事实是否保留、返回是否原位 |
| 交通 | 飞行卡、铁路/巴士/自驾等适用子模块 | 时区、横滑、切换状态和实际提示是否正确 |
| 清单 | 分类、增删改、勾选、保存 | 输入法、计数、撤销、刷新和失败是否可靠 |
| 首页 | 入口、场景、叙事动效 | 阶段、跳过、加载、终态和菜单是否正确 |
| 导航（必要时独立） | 菜单 DOM/作用域样式/切页逻辑 | 单一实例、目标页、返回、选中状态是否一致 |

几类模块可以合并，也可以少开任务。不要让首页和导航各造一份菜单；不要让交通与地图同时改同一弹层按钮。

## 3. 下发任务的最小契约

~~~text
任务：<模块及用户目标>
基线：<项目/分支/提交>
当前决定：<已确认行为与风格；列出刚被替代的旧要求>
范围：<允许的文件/函数/选择器；共享对象的负责人>
数据：<公开快照/真源；不得改的事实>
预览：<独立端口或部署；版本标识放工作回执，不污染产品>
完成条件：<真实操作与截图/状态证据>
回传：精确SHA、差异、新增/删除资源、测试、未测项。
只在本工作树提交；主任务集成和发布，不自行覆盖main。
~~~

独立端口避免串页；浏览器标签也要区分。不要多任务同时操纵同一个 Chrome 页面。需要共享浏览器动作时，明确“现在谁操作”，完成后归还。

## 4. 一个轻量调度表就够了

放在现有 travel.md 或工作记录中，不建额外后台：

| 需求/采用版本 | 模块任务 | 基线 | 实现提交 | 采用状态 | 集成提交 | 生产版本 | 未测项 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 用户明确修改 | 页面负责人 | SHA | SHA | adopted / exploring / superseded / rejected | SHA或空 | 部署/版本或空 | 一句 |

- 实现完成不等于用户采用。明确要求的小改可直接采用；审美探索按用户选择处理。
- 新需求覆盖旧需求时，更新“当前决定”，保留历史因果，但不让旧回执继续驱动实现。
- 每个已采用需求都有一个责任人和后续状态。用户说“所有未推的都推”，先筛出采用且完成的增量，排除探索、被否决版本和临时预览补丁。
- 如果“完成但未合入”出现，优先清掉积压；不能让跳过动画之类已授权需求不断停在“下一批”。

## 5. 任务回执要能直接用于集成

~~~text
采用需求：<一句>
提交：<精确SHA，父依赖SHA>
改动：<文件与函数/样式范围>
资源：<新增、删除、替换；许可与来源>
验证：<环境/尺寸/动作/结果>
未验证：<真机、网络或其他缺口>
预览：<URL和版本>
~~~

“最新分支 HEAD”不是足够稳定的交付：对方可能随后提交了探索页面。按精确 SHA 查差异，不误取后继。多个依赖提交按顺序处理；父链有废弃方案时，只取净正式差异，并记录映射。

## 6. 集成流程

1. 回读用户决定和差异，检查是否偷偷恢复旧字体、标题、长页、导航或旧数据。
2. 核对新增素材确实存在、已实际看过，没把参考图/私人图混入。
3. 对独立正式提交可拣选提交（cherry-pick）；部署分支已经推入远端主线时，保留真实祖先关系再整合，避免非快进。不要为省事 force-push。
4. 共享压缩文件发生冲突时，逐个功能块裁决。**禁止直接采用整个 ours/theirs，或只删冲突标记当解决完成。** 两端都是追加样式也要查重复选择器、优先级、过时规则和同名动画。
5. 手动移植 init 片段时保留主任务现行标题、数据来源、分页和其他初始化。核对元素已经删除时是否仍有空引用。
6. 汇总资源：新图、字体、许可、CSS、脚本都进正确白名单；被替换资源退出输出目录。不要靠“目录里有文件”猜它已上线。
7. 统一重建生成资源与缓存版本；检查受影响模块以及共享入口。纯 CSS 小改不必重复全部测试，导航/数据/状态变化需要相应回归。
8. 记录“来源SHA→集成SHA→构建版本”。拣选后的 SHA 不同不表示没合并；只有原分支未成为祖先也不能证明功能遗漏。

## 7. 防止旧预览反复制造问题

工作树中的旧全局 CSS、分页函数、字体和菜单，会让用户反复报告已经解决的问题。

- 每轮开始说清楚当前 URL 是哪个提交、哪个工作树。
- 模块负责人优先把干净的最新基线整合到自己的分支；有用户未提交修改时先保全。
- 临时只同步主分支字体/导航到预览，也要显式记录哪些文件是临时差异，最终提交排除重复内容。
- 给用户审阅整合效果时使用最新正式地址；工作树预览只用于新模块差异。
- 工具返回“已排队打开”只证明请求已安排。隐藏任务被打开后才会加载，不宣称已逐页浏览验证。
- 浏览器超时先保存状态和确认当前标签；不反复操作过期引用，不擅自修改系统代理或网络配置。

## 8. 发布批次与消息纪律

把逻辑完整、已验证的修改提交。把相近的已采用增量成组发布；用户紧急指出的阻断问题优先修。避免每一句状态回执都触发一次无意义完整部署。

发布完成需要四份证据：

1. 本地集成 HEAD 与远端目标分支一致。
2. 托管服务成功记录对应这个提交。
3. 原网址返回当前 HTML/变更资源的正确版本或哈希。
4. 受影响功能在正式页面表现正确。

初次发布可检查全清单；之后只检查改变的资源及受影响行为。生产服务返回旧边缘缓存时，区分构建没完成、旧 HTML 和旧资源，不能反复改随机查询串掩盖原因。

用户可见消息以结果、阻塞、待决策和下一步为主。未变化时安静等待，不逐条播报工具。完成一轮后报告一次整体结果。

## 9. 工具条件

有 Codex 桌面任务工具时：先列项目，确认 isGitRepository，再创建 project/worktree 任务；未提供确切 threadId 时不能把排队的 clientThreadId 当正式ID。已创建任务要观察启动结果。打开他人任务中的浏览器只在用户明确要求时指定该任务ID。

无这些工具时，使用本机 Git 工作树与可用执行环境，明确它们不会自动出现在某个应用侧栏。没有并行能力时串行执行同样的模块契约，不伪造代理或部署回执。
