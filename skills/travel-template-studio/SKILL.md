# 旅行模板与模块扩展

先判断需求需要改变哪一层。现有模板是起点，LLM可以生成新的代码；“字段存在”不是“功能已实现”。不把固定页面数、视觉风格或组件类型变成旅行限制。

| 需求 | 最小操作 |
| --- | --- |
| 已有结构适用，只改行程 | 从示例或本地旅行创建，修改`travel-data.json` |
| 同样功能，改变样式 | `npm run template -- --trip <dir>`复制独立模板，改该模板的CSS |
| 新页面、模块或行为 | 在该旅行模板中生成实际代码，补数据关系、路由、交互、失败与测试；列入manifest |
| 全新旅行/全新布局 | `npm run new -- --blank --trip <dir>`保留未知，再fork模板或指定另一模板；未知事实不能用示例订单补齐 |
| 复用自己的模板和数据起点 | `npm run new -- --from <existing-trip> --trip <new-trip>`，清查原日期、订单和隐私后再使用 |

运行：`npm run dev -- --trip <dir>`、`npm run build -- --trip <dir> --out <output> --manifest <outside-output.json>`。若存在`<dir>/template`，预览与构建自动使用它；也可显式`--template <path>`。自定义文件需列入`template/manifest.json`。复制模板是该旅行可恢复的分叉，不改公共模板。

## 实现契约

1. 阅读该模板已有的数据、渲染与状态代码，列出真正需要改的文件。先复用，不因新增模块重做全站。
2. 每个旅行事实只有一个权威来源。多个页面引用它；不得用相同文字复制出看似联动的第二套事实。租车使用`rentalRef`联动取还车事件。
3. 自定义页面同时处理入口、深链接、返回/刷新、可见状态、标题/语言、手机布局与打印/离线。页面存在但没有可达入口不算完成。
4. 自定义模块同时处理数据为空、数据变更、操作状态、失败恢复和来源。报销记录、票券勾选等本地状态必须说明不等于付款/预订或多人同步。
5. 不能靠通用校验器验证任意新业务字段。为新增逻辑写针对性测试，并用真实浏览器操作；生成新JS后检查它已打包和离线缓存。
6. 模板HTML保留构建所需标题/数据入口；基础构建读取对应模板的语言包和服务工作线程。全新技术栈可由LLM生成，但同时提供匹配的构建、预览和验收命令，不能冒用默认构建通过。
